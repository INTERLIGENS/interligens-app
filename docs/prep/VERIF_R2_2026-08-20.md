et `PutObjectLockConfiguration` figurent dans « Unimplemented bucket-level
operations ».*

## 3.1 — Les formes que R2 accepte · **VERIFIED (documentation Cloudflare)**

Une règle de Bucket Lock est un objet `{ id, condition, enabled, prefix }`.

**Portée — préfixe, oui.** `prefix` est optionnel ; *« Rules without prefix apply
to all objects in the bucket »*. Et — important pour une chaîne ouverte
rétroactivement — *« Rules apply to both new and existing objects »*.

**Trois conditions de rétention, et trois seulement :**

| `type` | paramètre | sens |
|---|---|---|
| `Age` | `maxAgeSeconds` | durée relative |
| `Date` | `date` (ISO) | **date absolue de libération** |
| `Indefinite` | — | jusqu'au retrait explicite de la règle |

*(`wrangler` : `--retention-days`, `--retention-date`, `--retention-indefinite`.)*

**Modes : il n'y en a aucun.** Pas de `governance` / `compliance` comme sur S3.
R2 n'a qu'un mode, sans nom. Le corpus documentaire complet de R2 ne contient
aucune occurrence de « governance mode », « compliance mode » ou « legal hold »
autrement que pour les marquer **non implémentés**.

**Jusqu'à 1 000 règles.** En cas de recouvrement, *« the strictest (longest)
retention requirement takes precedence »*.

**Aucun verrouillage du verrou.** C'est le point qui décide de tout le reste :
la règle **se retire librement et immédiatement** — tableau de bord (`…` →
Delete), `wrangler r2 bucket lock remove --id <RULE_ID>`, ou API. Il n'existe
**ni** palier irrévocable, **ni** durée plancher, **ni** délai de carence, **ni**
MFA-delete. Le changelog de lancement le dit lui-même : *« Lock objects
indefinitely, **until the lock is explicitly removed** »*. Quiconque détient un
jeton **Admin Read & Write** peut retirer la règle puis supprimer l'objet — deux
appels, sans délai, sans second facteur.

**Pas de versioning requis** — parce que **R2 n'a pas de versioning du tout**.
Divergence réelle avec S3, où l'Object Lock l'exige.

*Sources : `/r2/buckets/bucket-locks/`, `/api/…/buckets/subresources/locks/methods/update/`,
`/r2/reference/wrangler-commands/`, `/r2/api/tokens/#permissions`,
`/changelog/post/2025-03-06-r2-bucket-locks/`.*

## 3.2 — Ce qu'un verrou empêche EXACTEMENT · **VERIFIED**

| Opération | Bloquée ? | Preuve documentaire |
|---|---|---|
| **DELETE** de l'objet | **OUI** | erreur `10069` / `ObjectLockedByBucketPolicy` / **HTTP 403** — *« Object is protected by a bucket lock rule and cannot be modified or deleted »* |
| **Remplacement (re-PUT même clé)** | **OUI** | *« Bucket locks prevent the deletion **and overwriting** of objects »* ; l'erreur dit *« cannot be **modified** or deleted »* |
| **Expiration par règle de cycle de vie** | **OUI — le verrou gagne** | *« Bucket lock rules take precedence over lifecycle rules… the object will not be deleted until the 90-day requirement is met »* |
| Vidage / suppression du compartiment | **OUI, par ricochet** | *« A bucket cannot be emptied while any bucket lock rules are configured »* — et un compartiment doit être vide pour être supprimé |
| Téléversements multipart | oui | la règle porte sur *« objects/uploads »* |
| Suppression de dossier depuis le tableau de bord | oui | explicitement documenté |

**Réponse directe à ta question : suppression ET remplacement, les deux.** Ce
n'est pas seulement un anti-suppression.

**Ce qu'il ne bloque pas, et qu'on croirait :**

1. **Il ne se protège pas lui-même.** C'est LA différence de fond avec le mode
   *compliance* de S3. Contre un accident, une règle de cycle de vie oubliée,
   un script maladroit : efficace. **Contre quelqu'un qui détient les
   identifiants : deux appels d'écart.**
2. Pas de rétention par objet, pas de *legal hold* individuel.
3. Le retrait de la règle est **une édition de configuration ordinaire** — donc
   pas de piste d'audit privilégiée du type « bypass ».
4. **La documentation est muette** sur : les transitions de classe de stockage,
   `CopyObject` sur une clé verrouillée, et l'horodatage de référence d'une
   condition `Age` (téléversement ? dernière modification ? création de la
   règle ?). → **UNKNOWN**, et le troisième point compte pour une chaîne
   probatoire.

**Et il n'y a aucun filet derrière.** *« Deleting objects from a bucket is
irreversible »*. Pas de versioning, pas de corbeille, pas d'undelete, aucune
récupération documentée côté support. La page Durabilité le dit sans détour :
*« Durability does not prevent intentional or accidental deletion of data. Use
bucket locks and/or bucket-scoped API tokens »*. **La prévention est le seul
recours offert.** C'est pourquoi la pièce du 20 juillet est perdue : il n'y a
rien à interroger.
